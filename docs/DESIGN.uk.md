# Corundum HFT: архітектура

Тут описано розмітку спільної пам'яті, протокол між писарем і читачем і те, чому він коректний на процесорах зі слабким порядком операцій. Першоджерело: [corundum.h](../include/corundum/corundum.h) і [corundum.c](../src/corundum.c).

## 1. Розмітка сегмента

```
зміщення розмір  вміст                                     хто пише
0        128     magic, версія, розмір заголовка,          crd_create (один раз)
                 місткість, час створення, прапорці
128      128     head, notify_seq (слово futex),           писар
                 writer_pid, writer_closed
256      128     tail, reader_waiting, reader_pid          читач
384      128     резерв
512      C       область даних, C = місткість (степінь 2)  писар (записи)
```

Кожен блок має 128 байтів, а не 64: ядра Intel підвантажують кеш-лінії парами, тож два «гарячі» поля на відстані 64 байти все одно можуть заважати одне одному. Писар і читач ніколи не пишуть в один 128-байтовий блок.

`head` і `tail` є 64-бітними лічильниками байтів, які лише зростають. Зміщення в області даних дорівнює `pos & (C - 1)`. При 10 ГБ/с 64-бітний лічильник переповниться приблизно через 58 років, тому переповнення лічильників не обробляється.

- `head - tail` = зайняті байти, завжди `<= C`.
- порожньо: `head == tail`. повно: між `head` і `tail + C` немає місця для наступного запису.

## 2. Записи

```
+----------------+----------------+---------------------------+--------------+
| size: uint32   | type: uint32   | дані (size байтів)        | вирівнювання |
+----------------+----------------+---------------------------+--------------+
 <-------- 8 + align8(size) байтів, початок вирівняно на 8 байтів ---------->
```

- Дані вирівняні на 8 байтів, тому будь-який тип з `alignof <= 8` можна читати на місці.
- `type` визначає користувач; `0xFFFFFFFF` зарезервовано для заповнювача.
- **Записи ніколи не переходять через кінець.** Якщо запис не вміщується між поточним зміщенням і кінцем буфера, писар заповнює залишок записом-заповнювачем (`type = 0xFFFFFFFF`, `size = залишок - 8`) і кладе запис у зміщення 0. Залишок завжди кратний 8 і не менший за 8, тож заголовок заповнювача завжди вміщується.
- Максимальний розмір даних `C/2 - 8`. Запис загальним розміром `T <= C/2`, якому потрібен заповнювач, втрачає менше ніж `T` байтів, тому заповнювач разом із записом ніколи не перевищують `C`, і найбільший запис завжди можна записати, щойно буфер спорожніє.

## 3. Протокол

Писар, локальний стан процесу: `head` (власна копія, включає підготовлені записи), `tail_cache`.

```
reserve(n):
    T     = 8 + align8(n)
    start = head або наступне кратне C, якщо запис перетне кінець
    if start + T - tail_cache > C:
        tail_cache = load_acquire(shm.tail)            // (A)
        if start + T - tail_cache > C: return FULL
    записати заголовок заповнювача, якщо start != head
    return data + (start mod C) + 8
commit(n, type):
    записати size і type у заголовок запису
    head = start + 8 + align8(n)
    store_release(shm.head, head)                     // (B)
```

Читач, локальний стан процесу: `cursor`, `head_cache`.

```
read():
    if cursor == head_cache:
        head_cache = load_acquire(shm.head)           // (C)
        if cursor == head_cache: return EMPTY
    перевірити й прочитати заголовок запису в cursor; пропустити заповнювач
    cursor += 8 + align8(size)
    return вказівник на дані
release():
    store_release(shm.tail, cursor)                   // (D)
```

`crd_stage` дорівнює `commit` без (B), а `crd_publish` дорівнює самому (B), тож N записів коштують один запис із release. Так само N викликів `crd_read` і один `crd_release` коштують один запис.

## 4. Чому це коректно

Потрібні дві властивості, і кожну забезпечує одна пара acquire/release.

**Читач ніколи не бачить напівзаписаного запису.** Писар заповнює дані й заголовок звичайними записами, а потім виконує запис із release (B). Завантаження з acquire (C), яке бачить нове значення `head`, синхронізується з (B): усе, що записано до (B), видно всьому, що виконується після (C). Тому читач бачить повні заголовки й дані всіх записів нижче `head`.

**Писар ніколи не перезаписує запис, який ще читають.** Читання запису відбувається до запису з release (D). Завантаження писаря з acquire (A), яке бачить новий `tail`, синхронізується з (D), тож подальші записи писаря в це місце відбуваються після читань читача. Запис із release впорядковує попередні *читання* так само, як і записи, а саме це тут і потрібно.

Інших спільних змінних у передачі даних немає, тому на гарячому шляху немає атомарних операцій «читання-зміна-запис», блокувань і compare-and-swap. На x86-64 acquire-завантаження і release-записи компілюються у звичайні інструкції `mov`, на arm64 у `ldar` і `stlr`. Задача CI для arm64 існує тому, що пропущений бар'єр на x86 непомітний (x86 переставляє лише записи після читань), а на arm64 проявляється швидко.

**Кешовані позиції** (`tail_cache`, `head_cache`) можуть лише відставати від справжнього значення. Застарілий `tail_cache` змушує писаря вважати буфер заповненішим, ніж він є, і перечитати значення; застарілий `head_cache` змушує читача вважати, що даних менше, і перечитати. Жодне з цього не призводить до переповнення. В усталеному режимі писар звертається до кеш-лінії читача приблизно раз за оберт буфера, а не на кожне повідомлення.

## 5. Блокування: очікування і пробудження через futex

Активне опитування дає найменшу затримку, але повністю займає ядро. `crd_wait` дозволяє читачу заснути, при цьому писар, чий читач не спить, нічого за це не платить.

```
читач (crd_wait)                       писар (crd_notify, після публікації)
  s = load(notify_seq)                   (head уже записано з release)
  store(reader_waiting, 1)               fence(seq_cst)
  fence(seq_cst)                         if load(reader_waiting):
  if head != cursor: return OK               fetch_add(notify_seq, 1)
  futex_wait(&notify_seq, s, timeout)        futex_wake(&notify_seq)
```

Це схема Деккера: кожна сторона записує свій прапорець, ставить повний бар'єр і читає прапорець іншої сторони. З послідовно узгодженими бар'єрами принаймні одна сторона бачить запис іншої. Або читач бачить новий `head` і не засинає, або писар бачить `reader_waiting = 1` і будить його. Якщо писар збільшить `notify_seq` між читанням `s` і викликом `futex_wait`, ядро побачить `notify_seq != s` і одразу поверне керування. Жодне пробудження не губиться; саме це перевіряє тест у `test_ipc` із 20 000 записів і сплячим читачем.

Коли читач не спить, `crd_notify` коштує один бар'єр (`mfence` або інструкція з префіксом `lock` на x86, `dmb ish` на arm64) і одне читання, без системного виклику. Використовується спільний futex (без `FUTEX_PRIVATE_FLAG`): ядро ідентифікує його за фізичною сторінкою, тому він працює між процесами.

### Windows

Бекенд для Windows зберігає ту саму розмітку і той самий гарячий шлях; змінюються лише налаштування й сон:

- Сегмент є відображенням файлу підкачки з іменем `Local\corundum.<ім'я>` (простір імен поточного сеансу входу, особливих прав не потрібно). Windows видаляє відображення, коли закривається його останній дескриптор, тому процес-творець тримає один дескриптор у невеликій фіксованій таблиці (без купи) до `crd_unlink` або свого завершення.
- `crd_wait` / `crd_notify` використовують іменовану подію з автоскиданням `Local\corundum.<ім'я>.wake` замість futex. Рукостискання Деккера не змінюється. Подія з автоскиданням лишається сигнальною, доки її не «спожиє» очікування, тож `SetEvent` між перевіркою читача і `WaitForSingleObject` не губиться. Застарілий сигнал дає лише одне зайве пробудження, після якого читач перевіряє стан і знову засинає.
- Живість процесу в слоті писаря або читача перевіряється через `OpenProcess` + `WaitForSingleObject(handle, 0)`.

## 6. Життєвий цикл і збої

- **Створення атомарне для тих, хто відкриває.** `crd_create` використовує `O_CREAT | O_EXCL`, задає розмір сегмента, заповнює заголовок і записує `magic` останнім, з release. Процес, який бачить розмір менший за заголовок або `magic == 0`, отримує `CRD_ENOTREADY` і може повторити спробу. Неправильний magic або версія дають `CRD_EVERSION`; місткість, що не відповідає розміру сегмента, дає `CRD_ECORRUPT`.
- **Виключні ролі.** `writer_pid` і `reader_pid` захоплюються через compare-and-swap. Якщо в слоті записано процес, якого вже немає (`kill(pid, 0)` повертає `ESRCH`), слот перехоплюється. `CRD_OPEN_TAKEOVER` робить це примусово, для випадку повторно використаного pid або процесів у різних просторах імен PID.
- **Падіння писаря.** Опубліковані записи лишаються доступними для читання. Підготовлені, але не опубліковані записи втрачаються. Новий писар продовжує з опублікованого `head`.
- **Падіння читача.** Прочитані, але не звільнені записи буде доставлено ще раз наступному читачу, який починає з `tail`: після падіння читача доставка «щонайменше один раз», в інших випадках «рівно один раз».
- **Штатне закриття.** `crd_writer_close` публікує записи, встановлює `writer_closed` і завжди будить читача. `crd_wait` повертає `CRD_CLOSED`, коли буфер порожній і закритий; записи, опубліковані до закриття, ще можна прочитати.

## 7. Недовірена друга сторона

Читач припускає, що писар може бути помилковим або зловмисним:

- `head - cursor` має бути не більше `C` і кратним 8.
- Кожне слово заголовка читається рівно один раз атомарним завантаженням, а потім перевіряється: запис має лежати в межах опублікованого діапазону й не перетинати кінець буфера. Заповнювач має закінчуватися точно на кінці буфера.
- Будь-яке порушення повертає `CRD_ECORRUPT` без доступу до пам'яті поза відображенням.

Байти даних не захищені: писар може змінювати їх, поки читач на них дивиться. Читач, який не довіряє писарю, має скопіювати дані й перевіряти копію. Права доступу до сегмента (`mode` у `crd_create`, `0600` у прикладах) визначають, хто взагалі може підключитися.

## 8. Що не входить у задачі

- Кілька писарів або кілька читачів на одному буфері. Для цього на гарячому шляху потрібні операції «читання-зміна-запис»; використовуйте окремий буфер для кожної пари писар–читач.
- Зв'язок між машинами або між 32- і 64-бітними процесами.
- Довговічність: буфер живе в оперативній пам'яті.
- Великі сторінки (huge pages): сегменти POSIX `shm_open` використовують звичайні сторінки. Для дуже великих буферів `CRD_OPEN_PREFAULT` і `CRD_OPEN_MLOCK` прибирають з гарячого шляху page fault і витіснення на диск.
